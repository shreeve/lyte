## 0. Decisions for the owner — answer these before the wave rolls

The big ones are already made (4:4:4 leads; Work/Play with H4; 10-bit
deferred; ship before Sunshine stable; AV1 browser-only). These four are
genuinely open. Each has a recommendation; none is made unilaterally.

1. **How a session chooses Work vs Play (the wire mechanics).** Chroma
   is connect-time only (the capability registry's renegotiation rule:
   chroma/codec never move mid-session; a mode flip is a clean
   reconnect — pillar §2, LYTE-PLAN §2.2). Two candidate mechanics:
   - **(a) Declaration-as-choice (recommended).** The client declares
     exactly the chroma mode it wants this session: Play → `[420]`,
     Work → `[444]`. The negotiator's intersection IS the choice; the
     host opens the encoder posture the agreed set names. Against a
     host that can't do 4:4:4 the intersection is empty →
     `noCommonChromaMode`, a typed failure the client turns into the
     pillar's NAMED degradation: auto-re-dial declaring `[420]` plus a
     visible "4:4:4 unavailable on this host — running Play" banner.
     Zero new vocabulary, zero new vectors; costs one extra dial
     against pre-H4 hosts in Work mode.
   - **(b) A `preferredChroma` capability key** on the forward-compat
     spine (client declares `[420, 444]` support plus a preference the
     host honors). Cleaner semantics (support ≠ want), but it's a new
     registry key + appended vector cases + fold-in debt for the
     wire-v2 batch — machinery (a) gets for free.
   **Recommendation: (a).** If the extra-dial ergonomics ever hurt,
   (b) is a compatible later addition (unknown keys are ignored).
2. **The Work-mode conversion path preference order, and whether
   full-range is a hard bar.** §1 lays out the three encoder-input
   candidates. Recommended preference order for the V-1/V-2 probes to
   walk: **gbrp identity full-range → host-side BT.709 full-range
   YUV444 conversion → driver rgb_mode 4:4:4 (BT.601 limited)**.
   The open question the pillar forces: pillar §2 pins Work mode as
   full-range, but Stage A measured that NVENC's own RGB path is
   601-limited and signed it honestly. If gbrp fails on the client
   (the V-2 render risk) and the conversion leaf is judged too heavy
   for the first ship, is **4:4:4 at 601-limited an acceptable v1 Work
   mode** (chroma resolution win banked now, range upgrade later), or
   does full-range gate the ship? **Recommendation: chroma first —
   4:4:4/601-limited may ship if it passes every §7 gate except the
   full-range round-trip row, with the range row's status named in the
   gate report and the upgrade slice queued.** The ±2-code grating gate
   is the win 4:2:0 cannot match; range is recoverable later without
   wire surgery (VUI + client assert, no negotiation change).
3. **Does Work(4:4:4) keep the right to mint ceiling-sized frames?**
   HS-25's named question. The FEC ceiling prices protection at ~24
   datagram-milliseconds of wire per ceiling-sized (223,380 B) group at
   50 Mbps; if 4:4:4 fattens IDRs toward the ceiling routinely, capped-CQ's
   opening/RESTORE VBV cap decides whether those frames exist at all.
   **Recommendation: keep the HS-25 posture unchanged for Work** — the
   223,380 B cap stays, ceiling-sized frames stay legal-but-conformed,
   because Work-mode IDRs are structurally rare (infinite GOP,
   damage-driven — session start, unprotectable-latch re-anchors, and
   loss recovery only) and the ratchet erases any single IDR's quality
   debt within ~1–3 s. One 24 ms frame at session start is invisible;
   what would NOT be invisible is a permanently smaller VBV smearing
   every full-screen damage burst. V-1 books the 4:4:4 IDR/frame size
   distribution against the ceiling on the text corpus; the J-G4a gate
   requires `videoFramesUnprotectable == 0` across all legs. Revisit
   with a Work-specific VBV only if those numbers say so.
4. **The parallel track's gate coupling.** Clipboard v2 (P-1),
   multi-monitor (P-2), and dynamic resolution (P-3) are H4-assigned
   but none is 4:4:4-coupled. Does J-G4 (the H4 exit) require all
   three, or does the wave exit on the 4:4:4 core (J-G4a) with P-slices
   allowed to trail into the next wave? **Recommendation: J-G4 requires
   the 4:4:4 core + P-1 (clipboard v2 is cheap once F-2's bulk channel
   exists and it's the COMPARISON-widening feature); P-2/P-3 are
   in-wave but pre-declared droppable to H5** — the solo-maintainer
   arithmetic that kept H3 honest.
   **RULING UPDATE 2026-07-30: P-2 and P-3 DROPPED outright (owner).**
   P-2 has no user (single-screen reference host) and revives as
   connect-time session-parameter work with no wire debt if ever
   needed. P-3's scenario — the HOST desktop changing resolution
   mid-session — joins chroma under the established law: fixed at
   ANNOUNCE, change = clean reconnect. One residual belt named in
   HANDOFF: verify a live host geometry change tears down cleanly so
   the reconnect law engages. (The client scaling its window needs
   nothing; encoder downscale under deep-floor congestion is a
   separate, still-available idea.)

## 1. What is already true, what a probe must confirm

**Wire: 4:4:4 needs NO new vocabulary and NO new vector files.**
Verified in-repo at authoring:

- `CapabilityChroma.yuv444 = 2` has existed in LyteWire since W7
  (`Capabilities.swift`); `chromaModes` is a typed, REQUIRED key
  (key 3); empty intersection is already a typed negotiation failure
  (`noCommonChromaMode`).
- The frozen `capabilities-v1.json` **full-house vector already pins
  chroma `[1, 2]` encoding byte-exact** — declaring 4:4:4 exercises
  frozen wire bytes, it does not create new ones. Nothing regenerates.
- One trap, named so nobody trips it: `Capabilities.wireDefault`
  declares chroma `[1]` and its exact CBOR is the frozen `wire-default`
  anchor vector. **Do not edit `wireDefault`** — 4:4:4 declaration is a
  shell-side constructed capability set (the `declaringX()` posture the
  ends already use for keys 9/10/11), gated host-side on the empirical
  encoder probe (pillar §1's probe discipline).
- The stream's actual chroma is carried in-band by the SPS
  (`chroma_format_idc`), and the client already rebuilds its format
  description from in-band VPS/SPS/PPS on every IDR
  (`VideoRenderFactory`, `extensions: nil` — CoreMedia lifts the VUI).
  The wire's video path is chroma-agnostic by construction; HS-25
  re-proved the FEC/packetizer seam is byte-count-only.
- The pillar's full capability tuple (profile/bitDepth/matrix/range as
  typed keys) is **wire-v2-batch material** (the wire-v2 study already
  inventoried the Rext-tuple APPEND); v1 ships on chromaModes +
  in-band VUI + client assert. No wire-minor bump in this wave.

**Encoder (hevc_nvenc on the RTX 4050), verified against FFmpeg master
`nvenc.c` and the NVENC 13.1 application note:**

- Ada encodes HEVC 4:4:4 — **[verified]** (application-note feature
  matrix row "4:4:4 encoding: Y" for Ada; H.264 4:4:4 is CAVLC-only and
  irrelevant to us; HEVC 4:2:2 is Blackwell-only, also irrelevant).
- `hevc_nvenc` exposes `-profile rext` (`NV_ENC_HEVC_PROFILE_FREXT_GUID`)
  and sets `chromaFormatIDC = 3` for 4:4:4 input — **[verified]**
  (nvenc.c; the wrapper auto-selects Rext when the input is 4:4:4).
- Three input paths produce 4:4:4, with different color truths
  — **[verified in nvenc.c, measured truth needs the probe]**:
  1. **`gbrp` (planar RGB)**: encoded as GBR planes with **identity
     matrix** (`colourMatrix = RGB`) and `videoFullRangeFlag` honoring
     `color_range` — mathematically exact RGB in HEVC, zero matrix
     conversion, the pillar's 0/255 byte-exact round trip achievable
     BY CONSTRUCTION. Cost: capture hands us packed BGRx; a
     BGRx→planar repack (~473 MB/s at 2048×1280@60) must be built and
     measured **[probe: repack cost + encoder throughput]**.
  2. **`bgr0` + `rgb_mode=yuv444`**: the driver converts internally —
     zero host work — but nvenc.c **forces the VUI to BT.601 limited
     for packed-RGB input regardless of context settings** (the exact
     behavior Stage A measured on the 4:2:0 path). Chroma resolution
     win only; range stays studio-swing. **[probe: pup's libavcodec
     has `rgb_mode` — it's a newer wrapper option; and A/B-measure
     that the actual conversion matches the forced tag, Stage A's
     method]**.
  3. **Host-side BT.709 full-range YUV444 conversion** (CUDA kernel —
     Sunshine's `RGBA_to_YUV444` kernels from PR #4965 are the
     GPL→GPL reference — or CPU): full control, standard tags every
     decoder handles. Cost: a new conversion leaf, the largest build.
- Capped-CQ (`rc=vbr` + `cq` + maxrate) in Rext mode: nvenc.c shows no
  mode coupling, but rate-control behavior at 4:4:4 (QP walk, ratchet
  convergence, static keepalive size) is unmeasured — **[probe]**.
- Encode throughput at 4:4:4: NVENC 4:4:4 is slower than 4:2:0 per
  NVIDIA's own guidance; whether 2048×1280@60 + p4 + 4:4:4 holds the
  60 fps budget and the ~4.6 ms encode mean on THIS RTX 4050 is
  **[probe — the fps check R3 budgeted]**.
- `NV_ENC_CAPS_SUPPORT_YUV444_ENCODE` must return >0 on pup's actual
  driver (595.84) — the SDK matrix says Ada yes, the wrapper checks at
  open; a rejected open is loud **[probe]**.

**Client (Apple M5), verified against the community Rext support
matrix + Apple docs:**

- Apple Silicon hardware-decodes HEVC Rext 8/10-bit 4:0:0/4:2:0/4:2:2/
  4:4:4 (12-bit falls to software) — **[verified]** (StaZhu matrix;
  the M5 is current-generation, comfortably inside). Moonlight's 4:4:4
  falls to software decode on clients without GPU 4:4:4 (their #1852);
  ours rides hardware on the whole fleet — the structural win stands.
- `VTIsHardwareDecodeSupported` is codec-granular, not
  profile-granular — the pillar already mandates a REAL test decode as
  the client probe. What no document answers and only V-2 can:
  **[probe]** (i) does `CMVideoFormatDescriptionCreateFromHEVCParameterSets`
  + `AVSampleBufferDisplayLayer` accept and hardware-decode a Rext
  4:4:4 stream through our exact factory path; (ii) does the display
  path render **identity-matrix (GBR) full-range** content correctly,
  or does it mis-map matrix 0 (the gbrp path's one real risk);
  (iii) does the layer render 601-limited 4:4:4 correctly (it should —
  it's an ordinary matrix — but assert, don't assume); (iv) is there
  any silent chroma downsample between decoder and glass (readback
  through `VTDecompressionSession` is the referee, and becomes the §7
  harness's client half).

**The race, honestly (2026-07-28):** Sunshine's Linux NVENC 4:4:4
(PR #4965, merged 2026-06-16) now ships in **pre-release** builds
(v2026.704.34109 through v2026.726.710, all tagged pre-release; their
last stable, v2026.516.143833, predates it). The supremacy plan's
"master only" snapshot is one notch stale: the window to ship first on
a *released* Linux host is real but visibly narrowing. This wave's
ladder is ordered so the 4:4:4 core lands before the parallel track for
exactly that reason.

## 3. Wave structure — who runs where, what serializes

One coherent worker per package territory, never two in one package;
long live legs look stalled from transcripts — don't kill the quiet.

  pup (offline encode legs only — no live session, no 41151 contact,

  they GATE everything: no conversion-path code is written until the

  wave starts by making claims honest, not by building.

  starts the moment V-2's readback tap exists and banks the 4:2:0

  (root half) → V-5. J-G4a lands the moment V-4+V-5 are green — the
  headline gate is deliberately early, exactly like J-G3a: the
  Sunshine-race feature should not wait for the parallel track.
- **Wave 2 (parallel by territory).** P-1 is Wire/-led (a territory
  idle since F-2) with end-side halves; P-2/P-3 are Host/+root pairs
  taken serially by whichever worker holds those territories. Per
  owner decision 4's recommendation, P-2/P-3 are pre-declared
  droppable to H5 if the wave stretches.
- **Wave 3.** J-G4, one verification worker, no feature code touched —
  the H1/H2/H3 gate discipline exactly.
