# Lyte clipboard sync v1 — text both ways (the first H3 feature)

*2026-07-22. The clipboard-sync slice (CL-15 in the master plan's ladder,
row "Clipboard: portal Clipboard API on the RemoteDesktop session (host) +
NSPasteboard poll/consent UX (client)"). This document rules the v1 wire
shapes, the negotiation, the size/loop policies, and the user-facing
consent posture. It follows the pillar docs' spirit: small, explicit,
frozen-bytes-first. The protocol pillars stay the reference for carriage
semantics (`docs/20260720-191704-lyte-protocol-transport.md` §"Feature
channels", ARQ §; `docs/20260720-193000-lyte-protocol-overview.md`).*

## 1. Scope — deliberately small

v1 syncs **UTF-8 text**, both directions, while a session streams:

- Copy on the Mac → the host's clipboard holds the same text.
- Copy on the host → the Mac's pasteboard holds the same text.

**Non-goals, named (v2+):** images, rich text/HTML flavors, files
(CL-16's drag-and-drop owns file movement), primary-selection sync
(X11/Wayland middle-click), clipboard *clearing* (an empty clipboard is
not announced — see §3), lazy/on-demand transfer with MIME negotiation
(that arrives when clipboard moves to a real chan ≥ 8 feature channel,
§4), and a mid-session "stop announcing" wire message (§6's toggle is
local in v1; quieting the peer's announcements is a v2 courtesy).

## 2. Carriage — the ARQ ordered CTRL stream

Clipboard messages ride the **ARQ ordered stream (group 0)** on CTRL,
exactly like input and the audio-routing pair: reliable, exactly-once,
in-order — two rapid copies apply in copy order, and a clipboard set can
never reorder against the session control around it. The ARQ sublayer
segments and reassembles whole messages (its 256 KiB message budget
covers v1's ceiling with headroom), so **no clipboard-layer chunking
exists** — one clipboard change is one CTRL message.

The transport pillar's eventual home for features is one bidi stream per
feature on chan ≥ 8 ("a file transfer never blocks a clipboard paste").
v1 deliberately rides the CTRL stream both ends already run — the same
"carriage the ends possess today" ruling the idle frame recorded — and
bounds the head-of-line cost it accepts by the size ceiling in §3: a
64 KiB worst-case clipboard message is ≤ 60 segments, inside one ARQ
flight (send window 128), briefly delaying input events behind it but
never audio/video (they are not ARQ traffic). Moving carriage to a
feature channel later changes routing, not message bytes.

## 3. The wire vocabulary (frozen at this slice)

Two CTRL types, next free after 0x19; layouts are `type ‖ UTF-8 bytes`,
the text the sole trailing field (self-delimiting — the ARQ message
boundary is the length, the RetryHandshake1 precedent):

- **0x1A ClipboardSet** (client→host): "make this the host clipboard."
- **0x1B ClipboardAnnounce** (host→client): "the host clipboard changed;
  this is its content." Applied to the Mac pasteboard on arrival.

Same body, two types: direction-typed messages keep the role-confusion
drop loud (the 0x18/0x19 precedent) — a 0x1A arriving at the client or a
0x1B at the host is a protocol break, not weather.

**Validation, enforced at encode AND decode:**

- **Size ceiling: 65,536 UTF-8 bytes** (64 KiB). Rationale: the ARQ
  receive window describes 256 segments, and CTRL shares its ordered
  stream with input — the old 256 KiB sketch would nearly fill the
  window and stall keystrokes for ~4× longer for a payload class
  (giant copies) that a remote-desktop clipboard does not owe. Raising
  the ceiling is a v2/feature-channel discussion. Over-ceiling local
  copies are **suppressed, counted, never sent** (and never an error —
  copying a huge file's text is routine weather); over-ceiling wire
  bytes reject.
- **Valid UTF-8 or reject** (`invalidUtf8`, detected by byte-exact
  re-encode of the decoded string — the CBOR text rule reused).
- **Empty text rejects** (`emptyText`): v1 does not sync clearing, and
  a bare type byte is a zero-fill-adjacent bug to surface.
- Truncation (empty payload) and a foreign type byte reject with what
  they found. Never traps on hostile bytes.

## 4. Negotiation — capability key 10 on the W7 spine

**`CapabilityKey.clipboardText = 10`** (CBOR bool `true`), riding the
forward-compat spine through `unknownEntries` exactly like key 9: the
declaration appends one canonical `0A F5` map entry to whatever the end
already declares (the CBOR encoder owns canonical key order), survives
intersection **only on mutual byte-equal declaration**, and
`capabilities-v1.json` never moves. Absence is "not supported", never an
error. Folding it into the typed fields is a wire-version discussion.

Why not `featureChannels` (key 5, id 1 = clipboard)? That key promises
the transport pillar's chan ≥ 8 feature-channel architecture — its own
bidi stream, MIME negotiation, no-HOL-against-other-features — which v1
deliberately does not build. Declaring it for a CTRL-stream text sync
would be a lie a future implementation trips over; key 5 id 1 stays
reserved for the real feature channel. New semantics, new key (W7
rule 3, as designed).

Gating is the established rule-3 pattern, both ends:

- The host consumes 0x1A only when key 10 survived intersection —
  otherwise dropped **loud** (`.clipboardNotNegotiated`), never fatal.
  It emits 0x1B only under the same agreement (statuses are never
  volunteered to a peer that never asked for the key).
- The client refuses to send 0x1A **before a byte leaves** when key 10
  never survived, drops an unnegotiated 0x1B loud, and drops
  role-confused messages loud.

## 5. Loop prevention and dedupe — the sync book

The hazard: the host applies a client ClipboardSet to the OS clipboard;
the OS then reports a clipboard change (the portal signal, or the Mac's
`changeCount` bump); a naive watcher announces our own write back, and
the pair ping-pongs forever. LYTE-PLAN §5's discipline (content
suppression + dedupe) lands as one small sans-IO value type both ends
share verbatim — **`ClipboardSyncBook`** (LyteWire):

- `noteRemoteApplied(text)` — a remote set/announce was accepted for
  application: remember it in a short ring (capacity 8, oldest evicted)
  and clear the last-shared slot (the peer's clipboard has moved past
  whatever we last sent).
- `admitLocalChange(text)` — the watcher's verdict for a local change:
  - matches a ring entry → **`.suppressEcho`**, entry consumed
    (consume-once, so a user deliberately re-copying the same text
    later still syncs);
  - equals the last text we shared → **`.suppressDuplicate`** (dedupe:
    the peer already holds it);
  - otherwise → **`.share`**.
- `noteShared(text)` — a local change actually left on the wire: set
  the last-shared slot and clear the ring (once the local clipboard
  genuinely moved on, no earlier apply can echo anymore).

Proof obligation (pinned by tests on all three levels): a set must not
boomerang — host applies a client set, the OS change event for that
apply announces **nothing**; symmetrically on the Mac. The Mac glue adds
a second, cheaper guard: applying a host announce records the resulting
`changeCount`, so the poller skips its own write without reading it.

## 6. Consent posture — clipboards carry passwords

Clipboard sharing is privacy-sensitive; the recorded consent rule
(client build plan §5: "visible during the session") lands as the
host-audio-routing pattern:

- **Declaration ≠ consent.** Both ends always declare key 10 when built
  with the code (the capability says "speaks the dialect", mirroring the
  client's always-declared key 9); *sharing* is gated locally.
- **Client:** a per-host **"Share Clipboard" default** on the pinned
  store (`PinnedHost.shareClipboard`, optional — pre-slice files decode
  unchanged; nil/false = off; **default OFF**) seeds the session, and a
  **control-strip toggle** (visible only when key 10 survived
  intersection, the CL-13 gating) flips it live. While OFF, nothing
  leaves (local changes are not even read by the poller) and nothing
  lands (incoming announces are counted and ignored, never applied to
  the pasteboard).
- **Host:** the shell declares key 10 only when its clipboard leaf is
  enabled (the `--no-audio`/key-9 precedent) — a host without the leaf
  never negotiates the capability, so the client's toggle never exists
  against it.
- **Payloads are never logged** — events and stats lines carry byte
  counts, suppression verdicts, and counters, never content.

## 7. The host OS leaf — seam now, portal later

The real host clipboard is Wayland/portal territory: the primary plan is
the **portal Clipboard API attached to the existing RemoteDesktop
session** (host build plan §6 — selection-change signals + fd transfer,
both directions; `wl-clipboard` is not a real fallback on GNOME). That C
leaf is **out of scope for this slice** (Linux-only, pup offline). What
lands now is the Swift seam it will drive — `HostClipboardLeaf`
(HostWire): `apply(text:)` downward, an `onLocalChange` callback upward
— with a scripted implementation in the gate tests. The session core is
already complete against that seam: 0x1A consumption surfaces
`.clipboardSetReceived` (the shell applies via the leaf, the book
pre-armed against the echo), and the shell reports leaf changes through
`noteHostClipboardChanged`, which judges the book, the agreement, and
the ceiling before a 0x1B leaves.

## 8. Client glue — NSPasteboard, thin by design

NSPasteboard has no change notification: a ~200 ms `changeCount` poll
runs while the session streams **and sharing is on** (LyteUI's
`PasteboardSync`, shared by the app and wire-view). All policy — the
gate order (negotiated → enabled → book → ceiling), the counters, the
book itself — lives in the sans-IO `LyteUdpSessionCore`; the glue only
reads strings, applies strings, and swallows its own `changeCount` bump.
Known v1 gap, accepted: a copy landing in the same poll window as an
inbound apply is superseded by the apply (last-writer-wins at the OS
clipboard; the 200 ms window makes it rare).

## 9. Wire artifacts and the freeze policy

New codecs get a **new vector file, `clipboard-v1.json`** (vectorgen
grows the `clipboard` subcommand), rather than appending to
`control-v1.json`: the append path is legal under the freeze policy, but
control-v1.json's byte-exact pup verification is already queued on the
DEFERRED-PENDING-HOST ledger, and a new file keeps every committed byte
of the existing 12 untouched while that leg is in flight. Anchors: the
hand-computed bytes in `ClipboardCodecTests` (the codec never grades its
own homework). Inventory: roundtrips covering ASCII, multi-byte UTF-8,
and the exact 65,536-byte ceiling; rejects covering truncation, empty
text, both cross-type confusions, over-ceiling, and two invalid-UTF-8
shapes; the key-10 spine pinned as data (declared and absent), the key-9
file's precedent.

## 10. Observability

- Host: counters `clipboardSetsReceived`, `clipboardAnnouncesSent`,
  `clipboardAnnouncesSuppressed`; events `.clipboardSetReceived(text:)`,
  `.clipboardAnnounceSent(byteCount:)`,
  `.clipboardAnnounceSuppressed(reason:)` (loop-echo / duplicate /
  over-budget); drop reason `.clipboardNotNegotiated`.
- Client: counters `clipboardSharesSent`, `clipboardAnnouncesReceived`,
  `clipboardLoopSuppressed`, `clipboardIgnoredDisabled`,
  `clipboardDropsLoud`; event `.hostClipboardChanged(text)`;
  `shareLocalClipboard` returns a typed outcome.
- wire-view: `--clipboard` enables sharing (real NSPasteboard glue —
  the deferred live legs drive the whole loop without the app), the
  capabilities line names key 10, and the session stats line grows the
  clipboard counters. Byte counts only, never content.
