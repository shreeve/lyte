# Wire-v2 design study — the complete inventory of a version-2 batch, so that if it ever goes, it goes once (2026-07-28)

*Commissioned by H3 §0 owner decision 5 ("wire-version 2 batch: design-
discussion doc only in H3, no bytes change") — this is the D-5 rung of the
H3 plan (`20260723-051223-lyte-h3-plan.md`), executed as a docs-only
worker session against committed HEAD `4810720`. Zero bytes move; zero
code moves; every frozen vector file sleeps untouched. Authorities
unchanged: the pillar docs + overview are the protocol spec, the Lyte-UDP
decision record governs, `Wire/Vectors/README.md` is the freeze policy.
This study reads the ledger's wave block, the LyteWire source (which
carries zero TODO/FIXME markers — the debt lives in doc comments and
HANDOFF, all cited below), the supremacy plan, and the browser scoping
doc, and answers four questions: what debt exists, what the browser era
adds, how a v2 would actually negotiate, and — the ruthless cut — what
truly needs a major bump versus what the capability system was built to
absorb.*

## 0. Verdict, up front

**Nothing currently inventoried requires wire major 2. Recommendation:
NO-GO at every named horizon — not H4, not with 4:4:4's codec-profile
work — and a standing "never-unless" posture with the forcing functions
named (§6).** Twelve debt items were found (§2–§3); eleven ride the
capability keys / id lists / TLV escape hatches that were designed for
exactly this, and the twelfth (folding the per-datagram TLVs into fixed
envelope fields) is *defined* as v2-only by doctrine but is an economy
measure that cannot justify a bump on its own. The typed fold-in of
capability keys 9/10/11 — the item that started this discussion — turns
out to be **byte-invariant on the wire** (§2.1) and needs a vector-file
version plus at most a wire *minor*, never a major. The batch contents
are pre-written anyway (§6), so the day a genuine forcing item appears,
v2 ships everything in one bump.

## 1. The versioning machinery as actually built

Three layers, per the transport pillar §3 as amended by the Lyte-UDP
decision record §8.3 (no ALPN — the version moved into the handshake):

1. **Wire major** — `WireVersion.major = 1`. Rides as the first byte of
   the Noise message-1 *encrypted* payload, echoed in message 2 so both
   ends prove agreement inside the transcript; a mismatch aborts with
   `NoiseError.versionMismatch` before any transport key exists
   (`NoiseSession.swift`). TLV `0x02` is *reserved* for a plaintext-header
   carriage of the same number ("codec at W5") but was never assigned a
   live codec — the payload byte is the operative mechanism. **Finding:
   v1 has no downgrade or version-announce path on the wire** — a v2
   initiator dialing a v1 responder gets a silent abort, not a counter-
   offer. §4 weighs what that costs and why discovery already pays it.
2. **Wire minor** — capability key 1, u16, agreed = min, explicitly
   "information, not a gate" (`Capabilities.swift`). `wireDefault`
   declares minor **0**; it has never moved. Minors are compatible by
   construction — the unknown-key rule does the work.
3. **The forward-compat spine** — three rules lint-deep in the codec:
   unknown capability KEYS are ignored and preserved verbatim; unknown
   VALUES in id lists are carried, not rejected; new semantics ship as
   new keys gated by intersection. Plus the TLV escape hatches: the
   envelope's flags-bit0 TLV block and the feedback report's own TLV
   scheme ("the v1.x escape hatch", README). Doctrine, verbatim from
   `WireExtension.swift`: *"new per-packet fields land as TLVs first and
   fold into a fixed v2 envelope only at a wire-major bump."*

**What the freeze policy demands of any bump** (`Wire/Vectors/README.md`):
a committed vector file is frozen — new cases append, changed semantics
mean a NEW file version (`envelope-v2.json`) and a wire-version
discussion first; v1 files never regenerate. Fourteen frozen files exist
today, byte-exact on three attested platforms (macOS, Linux, and — since
the WASM probe — wasm32 under wasmtime). A v2 batch therefore carries a
per-file audit (§4.3), not a blanket regeneration.

## 2. The debt inventory, item by item

Each item cites its origin. "Fold-in" items are marked with what folding
actually looks like; the §5 table renders the cut.

### 2.1 Keys 9, 10, 11 — the raw-spine trio (items 1–3)

- **Key 9 `hostAudioRouting`** (HS-18 `6b5a78e` / CL-13, promoted at the
  codec promotion `65f56d0`): host-mute shipped as one canonical `09 F5`
  entry appended to `wireDefault`'s frozen encoding, riding
  `unknownEntries`, surviving intersection only on mutual byte-equal
  declaration. The promotion entry ruled: "deliberately NOT a typed set
  field in v1… the typed-field fold-in is a wire-version discussion"
  (HANDOFF; `Capabilities.swift:76–84`).
- **Key 10 `clipboardText`** (CL-15 `ce50a20`, `clipboard-v1.json`):
  same spine, same rule, `0A F5`.
- **Key 11 `bulkTransfer`** (W10 `7455911`, `bulk-v1.json`): same spine,
  `0B F5`; its doc comment already forwards the fold-in question here.

**What folding in properly looks like — and the finding that defuses
it.** Deterministic CBOR orders map keys bytewise-ascending, so a typed
`hostAudioRouting: Bool` encoded after key 8 lands in *exactly* the byte
position the appended spine entry occupies today: **the fold-in changes
zero wire bytes.** The intersection algebra is equivalent too, for the
bool case: byte-equal survival of `F5` (true∧true → present-true;
true∧false → dropped → absent → "not supported") produces the same
agreed outcomes as a typed AND. What changes is *decode decomposition*
(the key leaves `unknownEntries` and gains a typed field) — which is a
frozen-*semantics* change wherever a vector or test asserts the
unknown-ness of keys 9/10/11. Per the freeze policy that costs a
vector-file version for exactly the files whose assertions move
(audit in §4.3), plus a wire-minor bump as the honest marker. **It does
not need, and cannot justify, a major.** It also buys almost nothing:
the accessors in `AudioRouting.swift` / `Clipboard.swift` /
`BulkMessages.swift` already give both ends typed views. Ruling proposed:
the spine keys ride as-is indefinitely; fold them only as passengers on
a v2 that goes for a real reason.

### 2.2 Key 5 `featureChannels` — the dormant id list (item 4)

Typed ids clipboard = 1, fileTransfer = 2, printing = 3 were assigned at
W7 — and then clipboard shipped as key 10 (NOT id 1) and the bulk
mechanism as key 11 (NOT id 2), both deliberately: key 5's ids "promise
the chan ≥ 8 feature-channel architecture" (`Capabilities.swift`,
key-10/11 comments; CL-15 and W10 wave entries). With chan 8 now real
(W10), the registry needs a written reconciliation: ids name *chan ≥ 8
feature channels* (file drop qualifies once F-3/F-4 declare it;
clipboard v1 rides CTRL and does not), or key 5 stays dormant until a
feature actually multiplexes. Either way this is registry documentation
and (at most) an append — zero bytes, zero version pressure. Origin:
the key-11 doc comment names this exact question as D-5 territory.

### 2.3 The two pre-named APPENDs (items 5–6)

- **AV1 codec id `av1 = 2`** (supremacy plan `557ab78` R7 + its closing
  note "two named APPENDs (capability tuple, av1 id)"; browser scoping
  §3.1/B-4): `CapabilityCodec` assigned only `hevc = 1` and documented
  "AV1 lands as a new id when it lands"; the id list carries unknown
  values by rule, so a v1 peer drops it in intersection, harmlessly.
  **A vector APPEND, explicitly not a version bump** — the scoping doc
  says so verbatim, and owner decision B (2026-07-28) confirmed the
  `[hevc, av1]` browser offer. Lands with B-4.
- **The 4:4:4 capability tuple** (supremacy plan R3 Stage B / H4 wave
  444b: "capability tuple (vector APPEND)"): `chromaModes` already
  carries `yuv444 = 2` typed since W7. What Stage B actually adds is
  profile detail — HEVC Rext signaling, and later the 10-bit question
  (owner ruling 5: deferred until 4:4:4 converges). If codec+chroma
  alone underdetermine the decoder config, the clean shape is a NEW key
  (e.g. a `codecProfiles` id list), gated by intersection like
  everything else. Appends and new keys throughout; **H4's headline
  feature does not touch the wire version** — worth stating plainly
  because "do v2 with 4:4:4" was a candidate answer, and it is the
  wrong one.

### 2.4 HS-16's parked wire wants (items 7–8)

The estimator slice parked two items, verbatim from its wave entry:
"WIRE WANTS (deferred, no bytes moved): an RFC 8888-style per-report
ECN/marking field and an explicit receive-window/buffer-fill hint would
sharpen verdicts — both are wire-version items, parked" (HANDOFF, HS-16
entry). Re-examined against the built formats, *neither needs a
version*:

- **ECN/marking per report**: the chan-3 feedback report carries its own
  TLV block — "the envelope's exact TLV scheme… the v1.x escape hatch"
  (README) — with 77 B of headroom under the bounds-maxed encoding. An
  ECN section lands as a report TLV type, consumed when present, skipped
  by old hosts. Prerequisite honesty: the receive path must actually
  read ECN bits off the socket (a CNetIO cmsg leaf, host/client work)
  before the wire carriage means anything — the wire is not the long
  pole. Fold to a fixed report field only at an eventual v2.
- **Receive-window / buffer-fill hint**: same carriage, same rule — a
  report TLV. (The ARQ's own receive window is already described by ACK
  bitmaps; this hint is estimator food, not flow control.)

### 2.5 The doctrine-defined v2 item (item 9)

**Folding per-datagram TLVs into fixed envelope fields.** Two TLVs ride
production datagrams today: `connectionId 0x01` (migration) and
`lastInputSeq 0x03` (stamped per-shard, HS-13/CL-9). The doctrine
reserves their fold-in — plus an eventual ECN field — for the fixed v2
envelope. The economy: 2 + len bytes per TLV per datagram (the conn-id
and input-seq stamps together cost ~12 B against a 1152 B budget, ~1%).
This is the ONLY item on the inventory that is v2-by-definition — and
~1% wire efficiency is nowhere near a forcing function. It defines what
a v2 envelope *contains* when v2 goes for another reason; it never
*causes* v2.

### 2.6 Bookkeeping (item 12, stated here to keep §3 clean)

`wireDefault` declares wireMinor 0; no minor has ever shipped. The first
real minor bump should ride the first vector-file-versioning event
(likely the fold-in, if ever) so the number means something. Also noted:
envelope flags bits 1–7, fec-field byte 7, and chans 5–7 are reserved
headroom — reserved space is anti-debt; it needs no batch.

## 3. Browser-era pressures (items 10–11)

The browser scoping doc (`20260728-054139`) puts WebTransport carriage
on the H3 board (B-2…B-4, currently sequenced behind F-3/F-4 by owner
direction). Two genuine wire-adjacent needs, one non-need:

- **Item 10 — datagram-MTU negotiate-down.** A WT datagram must fit one
  QUIC packet: roughly 1150–1180 B browser- and path-dependent, so 1152
  "probably just fits; 'probably' is not a gate" (scoping §2). The
  existing mechanism cannot express DOWN: key 8 `maxDatagramBytes` is a
  *ceiling* with a hard floor — the codec **rejects** any declaration
  below 1152 (`CapabilityError.datagramCeilingBelowFloor`, pinned by the
  frozen `ceiling-below-floor` reject vector), and the one renegotiation
  path is a host→client *raise*. So if B-2's measurement lands under
  1152 in any engine, the ruling this study pre-writes: **a NEW
  capability key** (say `datagramBudgetDown`, u32 < 1152, agreed = min
  with 1152 absent-default) that shrinks the shard-geometry budget at
  the packetizing seam — the envelope encoder's ≤1152 checks are
  ceilings and already admit smaller datagrams, so only geometry policy
  moves, exactly the DPLPMTUD-shaped session parameter the budget
  comment reserved ("downward instead of up", scoping §2). Old ends
  ignore the key harmlessly — and can never meet it anyway, since the
  WT leaf and the Web client ship together (§4.1). **Convergent
  evidence this key earns its keep beyond browsers:** HS-16's deep-floor
  note independently wants "smaller video datagrams via DPLPMTUD-down…
  if a real path ever pins us that low" (HANDOFF). One key, two
  customers. Absorbs; no version.
- **Item 11 — a transport-binding capability.** A browser session
  differs from a native one in ways policy may want to know at
  negotiation time: no DSCP from a page, WT datagram budget, WebCodecs
  decode profile quirks. If B-3/B-4 need the host to know "this peer
  rides WT", that is one more new key (a carrier id, or folded into the
  negotiate-down key's presence) — declared by the Web client, ignored
  by old hosts. Named here so the B-slices don't bolt on an ad-hoc CTRL
  message instead. Absorbs; no version.
- **Non-item — certificate hashes.** The self-minted rotating ECDSA
  P-256 cert and its SHA-256 hash (owner decision C: host serves the
  page, hash embedded at page load) live entirely in the WT/TLS layer
  and the page-serving UX. The Noise layer above is byte-identical —
  the scoping probe proved the handshake the browser runs is the one
  pup already speaks. Zero envelope/handshake impact; recorded so
  nobody invents wire bytes for it.

## 4. Versioning mechanics — how a v2 would actually go

### 4.1 Negotiation, old-end/new-end, honestly

The mechanism as built: major byte inside Noise msg1's encrypted payload
→ a v2↔v1 dial is a hard `versionMismatch` abort with no counter-offer.
Three facts make this acceptable rather than scary:

- **The LAN-first no-fleet reality.** Both native ends ship from one
  repo and deploy together (the H2-exit posture: Lyte↔Lyte is the only
  path). There is no fleet to skew. The one laggard is the **browser
  client** — a cached page can be older than the host serving it — but
  the host serves the page (decision C), so page and host version
  together; a stale cache draws a version refusal at worst once.
- **Discovery announces before anyone dials.** Bonjour `_lyte._udp`
  advertises "host identity key hash, protocol versions, and port"
  (transport pillar §4). A v2-batch prerequisite: make that TXT record
  carry the major list for real (e.g. `v=1,2`), so a client picks the
  dial version *before* the first datagram and the abort path is a
  never-in-practice backstop. Manual host:port entry falls back to
  dial-highest-then-retry-lower — one wasted round trip, LAN-cheap.
- **Dual-speak host, transitional.** IK lets the responder decrypt msg1
  regardless of the version byte's value, so one listener can accept
  {1, 2} during a transition and answer in kind (msg2 echoes the
  version). The client pins the negotiated major for the session. If
  friendlier failure is ever wanted, the reserved plaintext TLV `0x02`
  finally earns its codec: stamp the major on the first datagram's
  header so a mismatched responder can refuse cheaply and *name* its
  version, pre-crypto. That codec is itself an append (a reserved slot
  filling in), shippable before or with v2.

Old-client/new-host and new-client/old-host both reduce to: agree on the
lower major at discovery/dial time, then let capabilities gate features
within it — the same story as today, one integer earlier.

### 4.2 What stays true across any bump

Capability negotiation happens *inside* a major: a v2 session still
opens with declarations and intersection; v2 changes the fixed layouts
beneath (envelope fields, folded registry), not the algebra. Features
keep gating on keys, never on the version number — the version buys
layout, the keys buy behavior. That separation is why this study keeps
concluding "absorbs".

### 4.3 The vector-file plan for a v2 batch

Per the freeze policy — v1 files NEVER regenerate; they remain in the
repo, asserted, as the frozen v1 contract for as long as v1 is dialable:

1. **New files for changed layouts**: `envelope-v2.json` (the folded
   fixed envelope: conn-id, lastInputSeq, ECN-if-proven — item 9),
   `capabilities-v2.json` (the enlarged typed registry: 9/10/11 folded,
   key-5 reconciliation written into the registry table), and a
   `control-v2.json`/`clipboard-v2.json`/`bulk-v2.json` **only where
   audit shows an assertion moved** — the spine pins in those files fix
   *bytes* (which the fold-in provably does not move, §2.1), so the
   audit enumerates which vectors also assert unknown-ness (e.g.
   `unknownKeyCount`-style fields) and versions exactly those files,
   nothing else.
2. **Untouched files stay untouched**: fec, video, beacon, noise,
   session, arq, lifecycle, pairing, retry — nothing in this inventory
   moves their layouts. If a v2 batch ever grows an item that does
   (AEAD suite, seq widths), the same rule applies file by file.
3. **Both-generations green in one suite**: the v2 files join the
   byte-exact three-platform gate alongside the v1 files (the
   `wireVersion` top-level field in every file already exists to make
   one suite hold both generations honestly). Vectorgen grows v2
   subcommands; v1 subcommand output stays anchored against the v1
   hand-computed bytes forever.
4. **Appends continue meanwhile**: `av1 = 2`, the 4:4:4 profile key,
   the negotiate-down key, report TLVs — all land as appends/new files
   under wire v1 on their own slices' schedules, before and independent
   of any v2. Nothing in this study queues behind v2.

## 5. The cut — needs-v2 versus capabilities-absorbs

The capabilities mechanism exists precisely to avoid version bumps; the
table is the proof it worked.

**Score: 0 items force v2. 11 absorb. 1 (item 9) is v2's reserved
content, waiting for a reason.** The genuine forcing functions, so the
posture is falsifiable — a v2 goes when a change cannot ride keys, id
lists, or TLVs: an AEAD/handshake suite migration (post-quantum,
Noise-pattern change), an envelope layout break (wider seq/frame fields,
restructured fec interior beyond byte-7), a datagram-budget architecture
change the TLV block cannot express, or TLV overhead measurably hurting
a real path. None is on any current plan.

## 6. Recommendation

- **Posture: never-unless.** No wire-v2 in H3, H4, or any named
  milestone. 4:4:4 explicitly does not need it (§2.3). The browser
  slices explicitly do not need it (§3). Revisit only when a §5 forcing
  function materializes.
- **Meanwhile, under v1**: `av1 = 2` lands with B-4 (owner decision B —
  already made); the 4:4:4 profile key lands with H4 444b; the
  negotiate-down key lands if-and-only-if B-2's measurement demands it
  (its gate already says "or the negotiate-down ruling written" — this
  study is that ruling's design half); ECN/receive-window ride report
  TLVs when the estimator work resumes and the socket leaf can read
  marks; keys 9/10/11 stay on the spine, permanently if need be.
- **The batch, pre-written for the day it goes**: fold TLVs 0x01/0x03
  (+ECN if proven) into the fixed v2 envelope; fold keys 9/10/11 into
  the typed registry; write the key-5 reconciliation into the registry
  table; assign the TLV-0x02 version-announce codec if not already
  shipped; new vector files per §4.3; discovery TXT carries the major
  list; transitional dual-speak host.
- **Owner decisions a v2 batch would need (none needed today):**
  (a) confirm the never-unless posture and the §5 forcing-function
  list; (b) bless the spine-keys-ride-indefinitely ruling (versus a
  standalone minor + vector-file version to fold them early — this
  study recommends against paying that vector cost for tidiness);
  (c) when the batch goes: the transition window for dual-speak, and
  whether the browser client's page-cache lag warrants the TLV-0x02
  refusal codec ahead of time.

*Nothing in this doc changes bytes, tests, or code. The next writer on
this subject should start from §5's table and delete rows that shipped
as appends in the interim.*
