## 3. Environmental finding 1 — the NVENC driver mismatch (and its shim)

The first live attempt died at encoder init: `OpenEncodeSessionEx
failed: unsupported device (2)`. Root cause: pup's unattended upgrade
moved the NVIDIA userspace to **595.84 at 00:42 tonight** (16 minutes
before the run started — `/var/log/dpkg.log`), while the kernel module
loaded at boot (Jul 21) stayed **595.71.05**. `dmesg` confirms `NVRM:
API mismatch` per attempt. gnome-shell holds the nvidia devices mmap'd,
so a module reload would kill the logged-in session (which portal
capture needs), and a reboot at 1 AM would strand the lock screen.

Fix (process-scoped, zero system changes): the superseded 595.71.05
debs were fetched from Launchpad librarian
(`libnvidia-compute/encode/decode/gl-595_595.71.05-0ubuntu0.26.04.1`),
extracted to `/tmp/nv571/ext/`, and every lyte-host run took
`LD_LIBRARY_PATH=/tmp/nv571/ext/usr/lib/x86_64-linux-gnu`. The subtle
part worth keeping: compute+encode alone were NOT enough — the kernel
kept seeing a 595.84 client until **`libnvidia-gpucomp.so`** (shipped
in libnvidia-gl) matched too; with it, NVENC encodes cleanly.

**The shim dies with the next reboot (it lives in /tmp) — and the same
reboot heals the mismatch properly, after which it must simply be
dropped.** Until then, any lyte-host run on pup needs that
LD_LIBRARY_PATH prefix.

## 4. Environmental finding 2 — media playback vs audible-mode cadence

Three consecutive HEAD runs (~01:21–01:28) measured hostAudible NIC
cadence far out of bound (35–79% outside 5±2 ms, inter-send bursts to
~43 ms) with **474 capture-stream xruns per 25 s** and the capture
callback at **1.4 ms busy** (normal: 0.2–0.5 ms), while the host
produced only ~150 of the expected 200 packets/s. The ALSA device
itself showed zero errors. A YouTube video (Chrome) was playing on
pup's desktop during that window — run E's client heard the mix
(−25.4 dBFS, ~1.8 kHz blend over the 440 Hz tone).

Attribution was settled by ladder, all on the same box within minutes:
pre-HS-18 (`6b5a78e^`), HS-18 (`6b5a78e`), promotion (`d98e154`), and
HEAD (`71d936b`) each rebuilt from git archive and measured — **all
clean once the media had stopped** (dev p99 0.407–1.303 ms, ≤0.6%
outside). Not a code regression at any commit; a transient
machine-state interaction while the media played (and/or its CPU
aftermath). Two durable observations:

- **hostMuted was immune even during the bad window** (0.354 ms dev
  p99, host audio queue delay 0.64 ms) — the null sink is graph-clocked
  rather than ALSA-IRQ-driven. One more argument for the muted posture
  as the streaming default.
- The capture callback runs without RT priority; under desktop CPU
  competition it misses 5 ms deadlines. **Deferred seam: RT/priority
  for the audio capture thread** (and re-measure audible-mode cadence
  under deliberate desktop media load).
